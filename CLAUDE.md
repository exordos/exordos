# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Exordos CLI (`exordos`) — a Python/Click command-line tool that is the client for the Exordos platform (server-side code lives in a separate `exordos_core` repo, not here). It builds project images, bootstraps local libvirt VM installs, and drives a running Exordos installation's REST API (IAM, secrets, compute, network, DNS, element management, backups, etc.).

## Commands

All commands run through `tox` (uv-backed). Do not invoke `ruff` or `pytest` directly for verification — go through tox so the locked environment is used.

```bash
tox -e py312              # run unit + functional tests on Python 3.12
tox -e ruff                # auto-fix lint + import order + format (ruff check --fix, format)
tox -e ruff-check          # lint only, no fixes (ruff check .)
tox -e mypy                # type check (mypy -p exordos) — do NOT run this; see below
tox -e docs                # serve mkdocs locally at 0.0.0.0:8181
tox -e cli_docs            # regenerate docs/cli/*.md from `exordos dumphelp`
tox -e bin                 # build standalone pyinstaller binary
tox                        # full matrix: coverage erase -> py3{10..14} + functional -> ruff/ruff-check/mypy -> coverage report
```

Direct pytest (once a tox env/venv is active), for iterating on a single test:

```bash
pytest exordos/tests/unit/some_test.py::test_name
pytest exordos/tests/unit/            # unit tests only
pytest exordos/tests/functional/      # functional tests (drive the CLI via CliRunner)
```

**Verification policy for this repo:**
- Linting: `tox -e ruff` (never call `ruff` directly).
- Type checking: skip entirely — do not run `mypy` or `tox -e mypy`.
- Tests: `tox -e py312` or `pytest exordos/tests/unit/` for the relevant scope.

Other:
```bash
make mdlint       # markdownlint-cli2 --fix over all *.md
make find_ascii    # grep for non-ASCII chars in comments (comments must be English)
```

## Architecture

### Entry point and command tree

`exordos/cmd/cli.py` defines the root `exordos` Click group and wires in every top-level command group (`iam`, `secret`/`s`, `compute`/`c`, `em`/`e`, `dns`, `network`, `vs`, `ua`, `repo`, `stand`, ...) via `ClickAliasedGroup` (`exordos/cmd/aliases.py`), which lets every group/command have short aliases (e.g. `exordos c` = `exordos compute`, `exordos iam u l` = `exordos iam users list`).

Each `exordos/cmd/<area>/` package mirrors a REST resource area server-side and typically has:
- `__init__.py` — defines the area's Click group and registers subgroups/aliases
- `<resource>/commands.py` — the actual commands for one resource

`ContextObject` (`exordos/common/cmd_context.py`) is attached to `ctx.obj` by the root command after resolving config: CLI flags > realm/context config file > defaults, via `settings_config` (`exordos/cmd/settings/config.py`) which supports multiple realms/contexts (like kubeconfig contexts). Auth, endpoint, project scope, and token TTLs all flow through this resolution before any subcommand runs.

Commands needing no server config (bootstrap, build, version, autocomplete, etc.) are listed in `COMMANDS_WITHOUT_CONFIG` in `cli.py` — add new config-free commands there.

### CRUD command factory

Most simple entity CRUD command groups (list/show/delete/clear) are NOT hand-written per resource — they're generated by `create_entity_group()` in `exordos/cmd/base.py`, given an entity name, its collection URL template (from `exordos/constants.py`), and a `FIELDS_MAP` for table display. See `exordos/cmd/iam/user/commands.py` for the canonical pattern:
1. Define `ENTITY`, `ENTITY_COLLECTION` (from `constants.py`), `FIELDS_MAP` (column header -> field name or extractor lambda).
2. `xxx_group = create_entity_group(ENTITY, ENTITY_COLLECTION, FIELDS_MAP)` gives list/show/delete for free.
3. Add custom commands (e.g. `add`, `update`) as plain `@click.command` functions and `xxx_group.add_command(...)`.

Nested/child collections (e.g. elements under a repository) use the `parents=[...]` argument to `create_entity_group`, which injects `--<parent>-uuid` options via `add_dynamic_parents`.

List/show output goes through `exordos/common/table.py` (`fill_table`, `print_table`, `show_data`) and supports multiple `--output` formats plus a `--watch` live-refresh mode (via `rich.live.Live`).

### API client layer

`exordos/clients/base_client.py` and `exordos/clients/base.py` wrap `bazooka` (HTTP client) with auth handling (password/token grants, OTP, refresh, token caching via `exordos/token_cache.py`, encrypted payloads via `exordos/common/crypto.py`). Command code gets an authenticated client with `base_client.get_user_api_client(ctx.obj.auth_data)` and calls generic helpers (`list_entities`, `get_entity`, `delete_entity`, etc.) rather than raw HTTP.

### Build / provisioning system

`exordos/builder/` implements the image build pipeline driven by a project's `exordos.yaml` (schema in `exordos/spec/schema.py`, validated against `exordos/spec/exordos_spec.yaml`/`base_manifest_spec.yaml` OpenAPI-style specs). `SimpleBuilder` (`builder/builder.py`) resolves dependencies (`builder/dependency.py`: local path, git, http, env-based deps) and delegates image creation to an `AbstractImageBuilder` implementation in `exordos/packer/` (Packer-based, one subfolder per OS profile: `debian_12`, `ubuntu_24`, `ubuntu_26`, `exordos_base`, etc.), templated via Jinja2 from `exordos/templates/`.

### Repositories, stands, backups, infra

- `exordos/repo/` — pluggable repo drivers for pushing/serving built element artifacts (`fs.py`, `nginx.py`, `local_server.py`), selected via the `exordos.repo.drivers` entry point group in `pyproject.toml`.
- `exordos/stand/` — models for a bootstrapped local installation ("stand").
- `exordos/backup/` — pluggable backup drivers (`local.py`, `s3.py`), selected via the `exordos.backup.drivers` entry point group; `backup.py` handles scheduling/compression/encryption/rotation logic shared across drivers.
- `exordos/infra/driver/` + `exordos/infra/libvirt/` — libvirt-backed VM provisioning used by `exordos bootstrap`.

New backup or repo drivers should be registered as entry points in `pyproject.toml` rather than imported ad hoc.

### Tests

- `exordos/tests/unit/` — pure unit tests, mock-heavy (e.g. `MagicMock(spec=...)` against builder/repo abstractions).
- `exordos/tests/functional/` — exercise the actual CLI via `click.testing.CliRunner` (see `tests/functional/conftest.py`); `tests/functional/utils/exordosctl.yaml` provides a fixture config; `tests/functional/cli/` mirrors the `cmd/` tree.
- `exordos/tests/manual/test_cli.py` — used by `tox -e cli_docs` to regenerate `docs/cli/*.md` from live `--help` output; not part of normal test runs.
- Coverage is aggregated across the full tox matrix (`begin`/`end` envs run `coverage erase`/`combine`/`html`/`report`); a single `tox -e py312` run alone won't produce the combined report.

## Code style

- 4-space indent, 88-char lines, double quotes, Ruff-managed import sorting (first-party = `exordos`, one import per line, sorted within sections) — all enforced/fixed by `tox -e ruff`.
- Type hints required on function signatures (even though mypy is not run in this workflow).
- Classes `PascalCase`, functions/variables `snake_case`, constants `UPPER_SNAKE_CASE`, private members prefixed `_`.
- Every source file starts with the Apache 2.0 header block (`Copyright 2025/2026 Genesis Corporation...`) — copy from a neighboring file.
- Comments must be written in English only (`make find_ascii` checks for stray non-ASCII in comments).

## Commit / PR conventions

Conventional commits: `<type>(<scope>): <subject>`, types `feat|fix|docs|refactor|test|chore`, scopes `cli|builder|repo|packer|tests` (extend naturally for other areas like `iam`, `backup`). PR titles use imperative present tense ("Add feature", not "Added feature"). Update `docs/` and `README.md` when CLI behavior changes; regenerate CLI docs with `tox -e cli_docs` and lint markdown with `make mdlint`.

## Working style expectations (from AGENTS.md)

- State assumptions explicitly; if multiple interpretations exist, present them instead of silently picking one.
- Minimum code for the task — no speculative abstractions, flexibility, or error handling for scenarios that can't occur.
- Surgical diffs: don't refactor or reformat adjacent code; every changed line should trace to the request. Only remove imports/vars your own change made unused — leave pre-existing dead code (mention it instead).
- Prefer verifiable goals ("write a failing test, then make it pass") over vague ones when scoping multi-step work.
